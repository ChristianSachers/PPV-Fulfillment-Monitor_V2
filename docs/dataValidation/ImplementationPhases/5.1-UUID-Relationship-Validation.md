# Phase 5.1: UUID Relationship Validation

## Outline

### What is Planned
Implement comprehensive cross-file validation that ensures data consistency between Campaign Setup files (XLSX) and Performance Reporting files (CSV). The system validates UUID relationships, enforces mutual exclusivity rules, parses hierarchical naming structures, and identifies orphaned records across both file types.

### Why it's Planned
- **Data Integrity**: UUID relationships between files must be consistent and valid
- **Business Rule Enforcement**: Campaign vs Deal mutual exclusivity prevents data corruption
- **Cross-File Consistency**: Names and IDs must match exactly between related records
- **Orphaned Record Detection**: Missing relationships indicate data quality issues requiring attention
- **Hierarchical Validation**: Campaign name structures require proper parsing and validation

### When Phase is Complete
- Campaign vs Deal mutual exclusivity enforced in reporting files (never both populated)
- Cross-file UUID consistency validated (Deal names match exactly between files)
- Hierarchical name parsing implemented for campaigns (" > " structure validation)
- Leading space stripping implemented for campaign name segments
- Campaign names without " > " handled properly (treat entire string as last segment)
- Orphaned record detection identifies UUIDs existing in one file but not the other
- All inconsistencies flagged for user attention with specific violation reasons

### Prerequisites/Dependencies
- Both campaignXLSXstructure.md and reportingCSVstructure.md specifications
- Phase 1.1 complete (Upload Processing Pipeline with both file parsers)
- Phase 1.2 complete (Record Classification Engine foundation) **← IMMEDIATE PREDECESSOR**
- Cross-file analysis capabilities in staging database
- **EXECUTION SEQUENCE**: Runs immediately after Phase 1.2 completion (parallel with Phase 2.1)
- **PARALLEL CAPABILITY**: Can execute alongside Phase 2.1 Summary Statistics Display

## Questions and Assumptions for Product Owner

### Questions Requiring Clarification

1. **Name Matching Tolerance**: Should Deal name matching be exactly case-sensitive, or allow for minor variations (case differences, whitespace)?

2. **Orphaned Record Handling**: Are orphaned records (UUIDs in one file but not the other) always errors, or can they be acceptable in some cases?

3. **Hierarchical Complexity**: How deep can hierarchical campaign names go? Are there limits to the number of " > " segments?

4. **Validation Priority**: Which cross-file validation failures should block approval vs. which should be warnings?

5. **Historical Context**: Should validation consider historical patterns of acceptable cross-file relationships?

### Assumptions Made

1. **Exact Matching**: Assuming Deal names must match exactly between files (case-sensitive, no fuzzy matching)

2. **Mutual Exclusivity**: Assuming Campaign ID and Deal ID are never both populated in performance records

3. **Hierarchical Structure**: Assuming " > " is the only hierarchical separator in campaign names

4. **Orphaned Records**: Assuming all orphaned records represent data quality issues requiring attention

5. **Validation Blocking**: Assuming cross-file validation failures should flag records as inconsistent but not block processing
