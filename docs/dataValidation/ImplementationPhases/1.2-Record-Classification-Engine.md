# Phase 1.2: Record Classification Engine

## Outline

### What is Planned
Implement a sophisticated record classification engine that analyzes each uploaded record and categorizes it into one of four distinct categories: New Entries, Updated Entries, Unchanged Records, or Inconsistent Data. This engine provides the foundation for user decision-making by clearly identifying what each record represents relative to the production database.

### Why it's Planned
- **Transparency**: Users must see exactly what each record means before approving changes
- **Safety**: Suspicious changes are flagged for review rather than automatically processed
- **Efficiency**: Unchanged records are identified and can be filtered out of displays
- **Business Intelligence**: Reasonable updates are distinguished from concerning changes

### When Phase is Complete
- Every uploaded record has a clear classification (new/updated/unchanged/inconsistent)
- New Entries are properly validated against business rules
- Updated Entries correctly identify reasonable changes with field-level tracking
- Unchanged Records are detected and counted but excluded from processing
- Inconsistent Data is flagged with specific violation reasons
- Classification results stored in staging database for dashboard consumption
- Cross-file validation identifies relationship inconsistencies

### Prerequisites/Dependencies
- Phase 1.1 (Upload Processing Pipeline) completed
- **INTEGRATION**: Extended staging tables from Phase 1.1 with additional classification columns
- **SHARED**: Unified processing response format compatible with Phase 1.1
- **REUSE**: Unified error code system building on Phase 1.1 foundations
- Production database access for comparison (read-only)
- **CRITICAL**: Combined upload enforcement - both Campaign and Performance files required
- Business rule specifications defined in this document

## Business Rules and Implementation Specifications

### Confirmed Business Rules (Product Owner Approved)

1. **Upload Requirements**:
   - **ENFORCE**: Combined uploads only - both Campaign and Performance files required
   - **REJECT**: Incomplete uploads missing either file type
   - Only accept complete entries to database

2. **Impression Change Rules**:
   - **ACCEPT**: Any impression increase >0 is reasonable
   - **FLAG**: Any impression decrease as suspicious/inconsistent

3. **Name Change Rules**:
   - **NEVER ACCEPT**: Deal name changes under any circumstances
   - **EXACT MATCH**: Case-sensitive string matching required
   - **NO FUZZY MATCHING**: Exact string comparison only

4. **Date Change Rules**:
   - **FLAG ALL**: Any date changes as inconsistent
   - **PURPOSE**: Allow users to derive new acceptable rules in future
   - **INCLUDES**: Start dates, end dates, any temporal fields

5. **Classification Priority**:
   - **PRIORITY 1**: Inconsistent data detection (trumps all other classifications)
   - **PERFORMANCE**: Production database queries acceptable during processing

### Business Rule Priority Order (Product Owner Approved)

**Conflict Resolution Priority (1 = highest priority, 9 = lowest priority):**

1. **Combined upload requirement enforcement** - REJECT incomplete uploads immediately
2. **UUID orphaning detection** - Identify records without production matches
3. **Cross-file relationship consistency** - Validate Campaign/Performance relationships  
4. **Impression decrease detection** - Flag any impression decreases as suspicious
5. **Deal name exact matching enforcement** - NEVER accept Deal name changes
6. **Date change inconsistency flagging** - Flag ALL date modifications
7. **Hierarchical name structure validation** - Validate " > " structure parsing
8. **Mutual exclusion rule violations** - Flag Campaign & Deal ID conflicts
9. **New entry business rule validation** - Validate new records against business rules

**Implementation Rule**: When multiple violations apply to the same record, apply the highest priority rule for classification and include all violations in the violation reasons list.

### Implementation Guidance for Backend Engineer

**Priority-Based Conflict Resolution Implementation:**

1. **Data Structures**:
   ```python
   class BusinessRulePriority(Enum):
       COMBINED_UPLOAD_ENFORCEMENT = 1
       UUID_ORPHANING_DETECTION = 2  
       CROSS_FILE_RELATIONSHIP_CONSISTENCY = 3
       IMPRESSION_DECREASE_DETECTION = 4
       DEAL_NAME_EXACT_MATCHING = 5
       DATE_CHANGE_INCONSISTENCY = 6
       HIERARCHICAL_NAME_STRUCTURE = 7
       MUTUAL_EXCLUSION_VIOLATIONS = 8
       NEW_ENTRY_BUSINESS_RULES = 9
   
   class ViolationResult:
       priority: BusinessRulePriority
       error_code: str  # Unified error code (VAL_*, BIZ_*, SYS_*)
       violation_reason: str
       record_id: str
       field_details: dict
       phase_context: str  # '1.1' or '1.2' for integration tracking
       
   # Integration with Phase 1.1 error codes
   class UnifiedErrorCodes:
       # Reused from Phase 1.1
       VAL_010 = "UUID not found in production"
       VAL_015 = "Invalid hierarchical structure" 
       VAL_020 = "New entry business rule violation"
       
       # New Phase 1.2 specific codes
       BIZ_101 = "Deal name modification not allowed"
       BIZ_102 = "Impression decrease detected"
       BIZ_103 = "Date modification flagged"
       BIZ_104 = "Cross-file relationship failure"
       BIZ_105 = "Combined upload incomplete"
       BIZ_106 = "Campaign/Deal ID conflict"
   ```

2. **Conflict Resolution Algorithm**:
   - Apply all applicable business rules to each record
   - Collect all violations with their priority levels
   - Use lowest priority number (highest priority rule) for primary classification
   - Store complete violation list for detailed user review and reporting
   - Generate priority-based recommendations for batch processing

3. **Implementation Pattern**:
   ```python
   def resolve_conflicts(self, record, violations: List[ViolationResult]) -> Classification:
       if not violations:
           return self.apply_standard_classification(record)
       
       # Sort by priority (1 = highest, 9 = lowest)
       violations.sort(key=lambda v: v.priority.value)
       primary_violation = violations[0]
       
       # INTEGRATION: Store in extended staging table
       self.store_extended_staging_data(record.id, {
           'phase_context': '1.2',
           'violation_details': {
               'primary_violation': {
                   'error_code': primary_violation.error_code,
                   'reason': primary_violation.violation_reason,
                   'priority': primary_violation.priority.value
               },
               'all_violations': [{
                   'error_code': v.error_code,
                   'reason': v.violation_reason,
                   'priority': v.priority.value
               } for v in violations]
           },
           'flagged_for_review': True,
           'variance_detected': True
       })
       
       return InconsistentClassification(
           record=record,
           primary_reason=primary_violation.violation_reason,
           error_code=primary_violation.error_code,  # Include unified error code
           all_violations=[v.violation_reason for v in violations],
           priority_level=primary_violation.priority,
           detailed_reasons=violations
       )
   ```

4. **Testing Requirements**:
   - Test each priority level individually
   - Test all possible priority combinations
   - Verify correct primary violation selection
   - Validate complete violation tracking
   - Test performance with large datasets and multiple conflicts
